# ADR-0001：Parser 后端选型 —— markdown-it-py + 自研插件，IR 作为稳定契约

- 状态：Accepted
- 日期：2026-08-15
- 关联风险：R-001（正则 Parser 不可持续）、R-002（Pandoc 二进制分发）、R-003（SourceMap 不完整）、R-018（多文件 include）
- 事实输入：`spikes/phase0/parser/REPORT.md`、`spikes/phase0/parser/results/coverage.json`、`docs/update/CURRENT_STATE_AUDIT.md`、`docs/update/IR_MODEL_DESIGN.md`

## 1. 背景与问题

ThesisForge 的编译管线是 `Markdown → ThesisDocument → Validation → Template → RenderPlan → DOCX`，Parser 是整个确定性与可诊断性的源头。现状（`docs/update/CURRENT_STATE_AUDIT.md` §2.1）：

- 现有 parser（`src/thesis_forge/core/parser.py`，396 行）为纯正则 + 逐行单遍扫描，无状态机抽象；
- 项目语法覆盖率最高（spike 覆盖矩阵 18 项中 15 支持 / 2 部分支持 / 1 不支持，见 `results/coverage.json`），行内位置精确到列；
- 但架构不可持续：未知语法静默降级为段落原文（D-01，`parser.py:379-384`）、块级对象只有行号（D-02，`parser.py:195,257,326`）、无多文件 include（D-06）；新增通用 Markdown 边缘语法只能靠继续打正则补丁——正是 R-001 描述的风险形态，其退路明确要求「不允许继续以正则补丁掩盖架构问题」。

需要决策的问题：V1 的 Parser 后端选哪条路线——A. pandoc JSON AST、B. markdown-it-py + 插件、C. 保留手写 parser 工程化加固——以及如何用契约隔离后端，使 model/validator/compiler/renderer 不随选型震荡。本 ADR 不覆盖 Region 显式语法、include 表面语法等开放问题（IR_MODEL_DESIGN §7 O-1/O-2，由后续 ADR 另行回答）。

Phase 0 parser spike（2026-08-14）为此提供了机械实证：依据 `docs/MARKDOWN_SPEC.md` 构造覆盖全部项目语法的单文件 fixture（front matter、1–4 级标题 + `{#id}`、六种 `:::` 容器、容器头 kv 元数据、单/多/带 locator citation、七种前缀 crossref、脚注引用/定义/续行、行内与块级数学、有序/嵌套列表、管道表），先经现有 parser 验证可完整解析（19 个 block、3 条 citation、7 条 crossref、2 条脚注），再由脚本逐后端机械提取覆盖矩阵与位置粒度（REPORT §1），结论不存在手工读 AST 的印象成分。

## 2. 决策

1. **目标后端迁移到 markdown-it-py（4.2.0）+ mdit-py-plugins（0.6.1）+ 自研插件**。项目专属语法由自写规则承担：
   - `::: kind {#id}` 六种容器（figure/table/equation/listing/algorithm/bibliography）：用 `container` 插件按名注册 6 次，容器头串原样保留后自行解析；
   - `[^label]` 脚注：用 footnote 插件（footnote_ref token 携带 label 元数据）；
   - `@fig:x` crossref 与 `[@key; ...]` citation：自写两条 inline rule（含段内偏移 → 行列换算，多 key 拆分与 locator 解析在规则内完成）。
2. **现有手写 parser 进入冻结维护**：
   - 只修 bug，不扩功能；新语法一律落到 markdown-it 后端；
   - 在 markdown-it 后端产出同一 Normalized IR 并通过双后端 diff 门禁前，它仍是默认后端，保障迁移期 `thesisforge build/validate/inspect` 全绿、不做大爆炸重写（IR_MODEL_DESIGN §6.2）。
3. **两个后端由 ParserBackend 协议隔离**（`docs/update/IR_MODEL_DESIGN.md` §6.1：`name / capabilities() / parse_file()`），**Normalized IR 是稳定 contract**：validator、compiler、renderer 只与 IR 交互，后端可替换而契约不变（IR_MODEL_DESIGN §1.2 P3）。
4. **pandoc 不作为编译依赖**。`thesisforge inspect/validate/build` 必须在无 pandoc、无网络的条件下工作（AGENTS.md §1.3）；pandoc 仅允许作为可选外部工具（如公式转换 provider，见 ADR-0003）在用户自行安装时启用，永不进入 pip 分发链与桌面安装包。markdown-it-py 与 mdit-py-plugins 版本进入锁定文件，保证解析行为可重复（spike 已实测确定性，§3.3）。

### 2.1 执行条款（谁、在什么版本前、做什么）

| 时限 | 责任方 | 动作 |
|---|---|---|
| 即刻（Phase 1 起） | core 维护者 | `core/parser.py` 转入冻结维护：只修 bug、不扩功能，新语法一律落到 markdown-it 后端 |
| Phase 2 完成前 | core 维护者 | 现有 parser 包装为 `legacy` 后端；markdown-it 后端实现 container 注册 ×6、crossref/citation 两条自写 inline rule、`{#id}` 提取与后端无关预检，产出与 legacy 一致的 Normalized IR |
| Phase 2 完成前 | QA | 建立 full-syntax fixture 双后端 diff 门禁（位置粒度差异只允许表现为 `approx` 标记差异）并接入 CI |
| Beta 前 | core 维护者 | Normalized IR contract 随 Beta 冻结（R-029）；后续变更走版本化与 deprecation 流程 |
| Phase 4 | core 维护者 | 删除 `legacy` 后端（或冻结为只读兼容 adapter） |

## 3. 决策理由

以下数字全部来自 `spikes/phase0/parser/REPORT.md`（2026-08-14，脚本机械提取，可复跑）与 `results/coverage.json`。

### 3.1 排除 pandoc 作为编译依赖（A 路线）

- **分发成本不可接受（R-002）**：pandoc 3.8.2.1 本机 arm64 单二进制 **253 MB**，无官方 pip 包；桌面端需按平台随包分发/签名，CLI 需用户自装或捆绑，还需锁版本保证可重复（REPORT §1、§4）。
- **sourcepos 与 citation 不可兼得（R-003 硬需求无法满足）**：
  - pandoc markdown reader 不支持 sourcepos 扩展，AST 位置覆盖率 **0%**，Lua filter 也无法补（REPORT §2.1 组合 M、§2.3）；
  - 唯一有位置的路线是 `commonmark_x+sourcepos`（行列 + 文件前缀），但该 reader **不支持 citations 扩展**，实测直接报错 `The extension citations is not supported for commonmark_x`（REPORT §2.1 组合 X、附录 A）；
  - 折中组合 M′（`markdown-citations`）实测 `@fig:x`、`[@key]` 全部保留为纯文本，可统一后处理，但仍无位置（REPORT §2.1）；
  - 即「原生 citation 节点」与「sourcepos」无法在同一趟解析中同时拥有（REPORT §2.1 关键事实），要位置就必须退回文本后处理 citation/crossref，抵消换后端的收益。
- **项目容器写法两种 reader 均不识别**：`::: figure {#fig:model}` 在 markdown 与 commonmark_x 下都静默退化为普通段落（fixture 中 5 个带 id 容器全部退化），必须预处理改写为 `::: {.figure #fig:model}`（约 20 行正则，改写后 6/6 恢复为 Div）——即 pandoc 路线同样要养一层预处理/后处理/预检代码（REPORT §2.2、§2.4）。
- 其他减分：脚注 label 在 pandoc Note 中必然丢失（pandoc Note 匿名、只按顺序编号，REPORT §2.2）；未闭合 `:::` 容器静默容错、退出码 0，诊断体系需完全自建（§2.6）；Table 子树在 commonmark_x 下完全无位置（含所有单元格，§2.3）。
- 覆盖矩阵对比（18 项语法特征）：A pandoc 10 支持 / 7 部分 / 1 不支持，并不优于 B（9/7/2），却附带 253 MB 与外部进程（fixture 级文档单次 subprocess + JSON 约 0.3 s）。
- Lua filter 不改变结论：它能在 pandoc 进程内做与 Python 后处理等价的变换，但**无法弥补 markdown reader 无 sourcepos 的缺陷**，且引入 Lua 维护面（REPORT §2.4）。
- pandoc 的多文件能力（`data-pos` 带文件名前缀且逐文件正确，REPORT §2.5）是 A 路线独有的真实优势，但不足以抵消上述三项硬伤；多文件 include 在 B 路线由 Project 层承担（§5.2）。

### 3.2 排除「手写 parser 加固」（C 路线作为目标后端）

- 现有 parser 覆盖率 15/2/1 确实是三者最高，行内行列齐全（fixture 全部 inline——citation/crossref/footnote_ref——实测均带 line+column，REPORT §2.3），但覆盖方式是不可持续的正则架构：R-001 评级 Critical，其触发信号已逐项在现状中出现——未知语法静默退化（D-01，`parser.py:379-384`）、块级行号无列（D-02，`parser.py:195,257,326`）、混合有序/无序标记硬截断列表块（D-05，`parser.py:346-347`）、无多文件 include（D-06）。
- 加固（块级列号、include、错误恢复、边缘语法测试）是增量成本，但每新增一条语法仍回到正则补丁模式。R-001 的退路条款明确「不允许继续以正则补丁掩盖架构问题」，因此 C 不能作为目标架构，只能作为迁移期的对照基准。
- 通用 Markdown 边缘语法（嵌套、转义、参考式链接等）在纯正则下需要长期补丁（REPORT §4 C 列），而 markdown-it 作为 CommonMark 兼容实现天然覆盖。

### 3.3 选择 markdown-it-py + 自研插件（B 路线）

- **真 token 流与插件机制**：块级 token 自带 `map=[start,end)` 行映射（0-based），替代手写逐行扫描；容器/footnote/attrs 等插件机制成熟，自写 inline rule 有公开 API（REPORT §2.3、§2.4）。
- **覆盖矩阵与 pandoc 持平且无硬伤**：18 项语法特征 9 支持 / 7 部分支持 / 2 不支持（两项「不支持」为行内位置与错误诊断，均可由自写规则与预检层补齐，见 §5.2）；对照 pandoc 10/7/1，差距在基础语法原生度，但项目专属语法（容器写法、crossref）反而只有 B 路线能低成本覆盖（REPORT §3、§4）。
- **项目容器写法原样兼容**：container 插件注册后 `info=' figure {#fig:model}'` 头部串原样保留，自行解析即可，无需 pandoc 路线那样的源码预处理改写（REPORT §2.4）。
- **footnote 插件保留 label**（footnote_ref token 携带 label 元数据），满足脚注 label 必须进入 ThesisDocument/IR 的要求——这正是 pandoc 路线必然丢失的信息（REPORT §2.2 vs §2.4）。
- **自写 inline rule 可拿列号**：`state.src` 为段落文本、`state.pos` 为段内偏移，配合宿主 inline token 的块级 `map` 可换算行列；spike 用约 30 行的 crossref demo rule 成功把 `@fig:model` 定位到行列（REPORT §2.3、§2.4），满足「行内行列齐全」的 IR 契约要求（IR_MODEL_DESIGN §2.1、§4.1）。
- **纯 Python wheel**：进入现有 pip 分发链，零原生依赖，无 R-002 问题；进程内调用，无 subprocess/JSON 开销（REPORT §4）。
- **基础语法靠插件齐全**：数学、表格、列表、脚注结构等通用语法由 markdown-it 核心与 mdit-py-plugins 覆盖，项目只需承担项目专属语法（容器头/crossref/citation）的扩展（REPORT §4 B 列）。
- **确定性实测通过**：同一输入两次解析 token 序列一致（`two_parses_token_equal=true`；三条路线均机械验证可重复，REPORT §2.7）。
- **迁移成本可控**：token→ThesisDocument/IR 映射层约 300–400 行 + 自写规则，项目语法扩展合计约 3–6 人日（REPORT §2.4、§4），低于 pandoc 路线（300–500 行映射 + 预处理/后处理/预检三层）。
- **迁移面收敛**：model/validator/compiler/renderer 不动，变动集中在 parser 包与 `tests/test_parser.py`（278 行，按新语义调整）；现有 482 项测试基线（2026-08-14 实测，`CURRENT_STATE_AUDIT.md` §4）构成迁移回归网。

### 3.4 与 IR 契约的衔接

本决策不是孤立换库，而是 IR_MODEL_DESIGN 的落地前提：

- ParserBackend 协议（`name` / `capabilities()` / `parse_file()`）使后端产出的节点集合允许是 IR 能力的子集，contract 测试按能力参数化（IR_MODEL_DESIGN §6.1）——spike 问题清单第 1/4/7 条（位置粒度、语法写法、Table 盲区）的验收口径由此固定；
- spike 问题清单第 10 条（`parse_markdown_text()` 公共契约冻结）由「Normalized IR contract」回答，冻结面从函数签名升级为 schema（IR_MODEL_DESIGN §6.1）；
- 后端内部完成位置换算（段内偏移 + 宿主 token map），IR 层只看到统一 SourceSpan，对后端无感知（IR_MODEL_DESIGN §6.1）。

## 4. 备选方案与拒绝理由

### 4.1 A. pandoc JSON AST（含 commonmark_x+sourcepos 变体）——拒绝为编译依赖

- 253 MB/平台的分发与签名成本（R-002），与「本地优先、确定性」的产品形态冲突；
- markdown reader 无 sourcepos（0% 位置覆盖）；commonmark_x 有位置但与 citations 扩展互斥，项目必须自写 citation/crossref 后处理（各 1–2 人日，REPORT §2.4），还要处理 pandoc 的私有行为——如 locator 中 `p. 12` 的空格被归一化为 nbsp（`p.\u00a012`）、多 key 拆分为多个 citation 项、wrapper Span 重组与 offset→pos 回映射（REPORT §2.2、§2.4）；
- 容器写法不识别需预处理、脚注 label 丢失、Table 位置盲区、错误静默容错——诊断与预检层照样要自建，「换成熟后端」的核心收益被抵消；
- 结论：pandoc 保留为**可选外部工具**定位（用户自装、系统路径发现、版本记录），不进入编译依赖与分发链。

### 4.2 C. 手写 parser 工程化加固 ——拒绝作为目标架构

- 覆盖率最高（15/2/1）但属 R-001 描述的不可持续形态；加固无法消除「新增语法 = 新正则补丁」的结构性问题；
- 保留价值：迁移期内它是唯一经过 482 项测试（含 parser 测试断言到列号）验证的后端，故转为冻结维护的 `legacy` 后端，作为双后端 diff 门禁的对照基准，Phase 4 再删除（IR_MODEL_DESIGN §6.2）；
- 加固项本身（块级列号、错误恢复、边缘语法）即使全部做完，也只能把 C 推到「加固的正则架构」，无法回答 R-001 的关闭标准中「技术决策已落实 + 架构可持续」的要求。

### 4.3 调整项目语法向 pandoc 兼容（如容器头改 `::: {.figure #id}`）——拒绝

- 语法是用户面契约，`::: kind {#id}` 已写入 MARKDOWN_SPEC 与示例；为迁就一个不作为依赖的后端改动用户语法本末倒置（REPORT §6 问题清单第 4 条）。

## 5. 后果

### 5.1 正面

- Parser 从正则单遍扫描升级为真 token 流 + 插件架构，R-001 获得可关闭的架构基础；
- Normalized IR 成为稳定 contract，model/validator/compiler/renderer 对后端替换免疫（IR_MODEL_DESIGN §6.1）；`parse_markdown_text()` 公共契约的冻结面从函数签名升级为 IR contract；
- 行内行列齐全的诊断定位能力在自写 rule 下得以保留并显式化（SourceSpan 行列 + approx 标记，IR_MODEL_DESIGN §4.1）；
- 分发链保持纯 Python，桌面/CLI 打包无新增原生依赖；进程内调用消除每次解析一次 subprocess + JSON 序列化的开销（pandoc 路线 fixture 级文档实测约 0.3 s/次，REPORT §4）；
- 双后端并存期天然形成 full-syntax fixture 的 diff 门禁（位置粒度差异只允许表现为 `approx` 标记差异），为 R-016 测试深度添一层保障；
- 「未知语法不静默降级」从规范要求变成可执行项：后端能识别但 V1 不支持的语法（粗体/链接/顶层代码围栏等）将产生结构化节点 + 诊断（IR_MODEL_DESIGN §1.2 P2），关闭 D-01。

### 5.2 负面（已接受的代价）

- **块级位置仅行号、无列**（markdown-it `token.map` 0-based 仅行；inline token `map=None`）：与现状（D-02）持平，不改善也不倒退；块级列缺省在 IR 中以 `approx=True` 显式标记（IR_MODEL_DESIGN §2.2、开放问题 O-3）。
- **attrs 插件不提取标题行尾 `{#id}`**（实测 attrs 为空、`{#id}` 残留文本中），需自行从 inline 文本提取（约 10 行，REPORT §2.4）。
- **迁移期双 parser 并存成本**：legacy 与 markdown-it 两套后端同时维护，直到 Phase 4 删除 legacy；期间任何语法行为变更需双端同步并通过 diff 门禁。
- **插件补丁维护责任**：插件自带 token（如 footnote_ref）不记录位置，要列号需 fork/补丁插件（约 0.5–1 人日，REPORT §2.3/§2.4），该补丁由项目自行维护并跟随上游版本。
- **错误诊断仍需自建预检层**：未闭合 `:::` 容器在 markdown-it 下静默吞到文末（REPORT §2.6），ParseError 语义（带行号）由后端无关预检承担（IR_MODEL_DESIGN §3.2 校验点 P0）——这一层在 A/B 两路线都不可避免，不是本决策新增的代价。
- **多文件 include 由调用层实现**：markdown-it `parse()` 只接受字符串；逐文件解析 + `SourceSpan.file` 消歧由 Project 层承担（IR_MODEL_DESIGN §2.4、§4.3），换取位置语义不出错。

### 5.3 后续行动

1. **Phase 1（IR 包与 adapter）**：按 `IR_MODEL_DESIGN.md` §6.2 建立 `core/ir/` 四层模型、SourceSpan/Origin、JSON 序列化与 `ir_version`；现有 `model.py` 不动，新增 model↔IR 双向 adapter；建立 Normalized IR contract snapshot（`qa/baselines/`）；Validator 输出经 adapter 补 span 雏形（file=source_path）。
2. **Phase 2（ParserBackend 协议落地）**：
   - 现有手写 parser 包装为 `legacy` 后端；
   - markdown-it 后端接入并产出同一 Normalized IR；
   - 实现三条自写规则（container 注册 ×6、crossref inline rule、citation inline rule）+ 标题 `{#id}` 提取 + 后端无关预检（未闭合容器、非法 front matter、非法 ID 字面量）；
   - 建立 full-syntax fixture 双后端 diff 门禁（位置粒度差异只允许表现为 `approx` 标记差异）；
   - Project 层实现 manifest + 逐文件解析 + 全局符号表，多文件 include 在此落地（R-018）。
3. **Phase 3（Compiler/Validator 切换）**：compiler 消费 Normalized IR、产出 Resolved IR，期间 RenderPlan 作为 lowering 产物保留、renderer 零改动（IR_MODEL_DESIGN §6.2）。
4. **Phase 4（收敛与冻结）**：删除 `legacy` 后端（或冻结为只读兼容 adapter），IR contract 随 Beta 冻结（R-029）。
5. 在 `docs/MARKDOWN_SPEC.md` 与 Parser 测试中固化「项目语法集合 + 未支持语法诊断」清单，杜绝静默降级（D-01、IR_MODEL_DESIGN §1.2 P2）。

  - mdit-py-plugins `container` 按六种容器名注册 ×6，`validate` 收紧为与 legacy `CONTAINER_START_RE` 等价（恰好 3 个冒号 + 可选 `{#id}` + 行尾无杂物）；容器体不读 mdit 子树，按源码行切片后复用 legacy `_parse_container` / `_parse_container_inlines`（kv 元数据、caption inline、listing 围栏剥离、`$$` 剥离逐字节一致）。
  - `footnote` 插件仅取块级定义（`inline=False` 关闭 `^[...]`、`move_to_end=False` 保持定义源码位置）；定义正文按 legacy 算法（首行 + 四空格/Tab 续行）从源码行重建；行内 `footnote_ref` 用 `ruler.at` 替换为与 legacy 字符集一致的自研实现（不要求定义存在）。

  - 块级仅保留 heading/list/paragraph + 上述插件；table（commonmark 预设本就不含）/fence/blockquote/html_block/hr/lheading/reference/code 禁用，使这些结构按段落原文降级，与 legacy 一致。
  - 列表：mdit 仅负责发现列表起点，随后按 legacy 逐行扫描（缩进 `//2` 层级、起始序号/ordinal、混合 marker 与空行分块截断）；mdit 把列表项续行并进项内段落时，跨界行区间按 legacy 补落为独立段落。
  - 未闭合容器由后端无关预检承担（与 legacy 主循环同构的行扫描），`ParseError("第 N 行的 X 容器未闭合")` 消息与行号逐字节一致；front matter 强校验直接复用 legacy `_parse_front_matter`。
  - SourceLocation：块级行号 = `token.map[0] + 1 + front matter 偏移`，column 恒 None（与 legacy 现状一致）；行内行列由自研规则记录的段内偏移经 legacy `_location_for_offset` 换算，与 legacy 完全一致。
  - `qa/tools/parser_diff.py` 新增显式豁免机制：`--allow PATTERN=REASON`（REASON 必填）+ `AllowRule`/`diff_documents()`，被豁免差异逐条带原因打印，杜绝无记录宽泛豁免。
  - 平价验收（`parser_diff.py`，legacy vs markdown-it，归一化逐字段 diff，**零差异、零豁免**）：`qa/fixtures/parser/full-syntax.md`（19 块/51 inline）、`examples/complete-thesis/thesis.md`（45 块/81 inline）、`examples/bachelor-thesis/thesis.md`（43 块/78 inline）、`examples/bachelor-thesis/thesis-full-template.md`（185 块/266 inline）。新增测试 `tests/test_parser_markdown_it.py`（32 项：协议/注册表/fixture 平价/22 个行内块级平价小样本/错误消息一致/降级一致/豁免机制）；pytest 590 全绿，ruff 无错。

  **已知差异清单**（均以 legacy 为准；均不在四个平价 fixture 与现有示例的语法面内，markdown-it 侧未对齐，对应 diff 门禁暂不豁免——出现时逐条评估）：
  1. 有序列表以非 1 起始序号**直接打断段落**（如 `段落\n2. x` 无空行）：legacy 截断段落另起 ListBlock；markdown-it 按 CommonMark 规则并入段落。
  2. 行首 4 个及以上空格缩进的容器起始行 / 列表行：legacy strip 后照常识别；markdown-it 侧按段落原文降级（indented code 规则已禁用）。
  3. 脚注定义的「空行 + 缩进续段」：legacy 只吞连续缩进续行、其后内容另成块；markdown-it 的 `footnote_def` 会把空行后的缩进段一并吞入定义区域，不再产出块。
  4. ATX 标题尾部闭合序列（`# 标题 ###`）：markdown-it 剥掉尾部 `###`，legacy 保留在标题文本中。
  5. 空标题（`#` / `# ` 后无文本）：markdown-it 产出空文本 Heading，legacy 降级为段落。
  6. label 含 legacy 字符集（`[A-Za-z0-9_.:-]`）之外字符的脚注定义（如 `[^注]:`）：legacy 将该行并入前段落；markdown-it 侧降级为独立段落，紧贴前文段落时分块边界不同。
