# ADR-0006：质量门禁、产品范围与兼容矩阵（六域证据制 + qa 门禁工具 + 分级兼容承诺 + V1 范围纪律）

- 状态：Accepted
- 日期：2026-08-15
- 关联 Phase：Phase 0（决策）→ 全周期（门禁执行）
- 关联风险：R-014 / R-015 / R-016 / R-019 / R-030（另关联 R-006/R-007/
  R-027/R-028 的兼容与 finalizer 维度）

## 1. 背景与问题

V1 优化计划要求质量「不仅测代码，还测 OOXML、视觉、办公软件兼容、
离线、安全和可复现性」（`docs/update/ThesisForge_优化计划_执行摘要.md`
决策 7）。现状缺口明确（`docs/update/CURRENT_STATE_AUDIT.md` §4–§5）：

1. 现有测试虽有 458 处 XML/XPath 结构断言（test_docx_renderer.py
   3102 行、test_acceptance.py 951 行），但**无跨软件 no-repair 打开
   门禁**（R-015：DOCX 包合法但 Word 仍提示修复，Medium × Critical），
   也无统一的用例目录、证据归档与基线治理（R-016，High × Critical）。
2. 没有定义对 Word/WPS/LibreOffice 的**承诺等级**——三者 OOXML 字段、
   OMML、页眉页脚行为存在已知差异（R-014，High × Medium），不定义
   等级就无法回答「什么算通过」。
3. 产品范围未被书面约束：项目面临「同时支持本科/硕士/博士/期刊/
   LaTeX/云协作/AI/模板市场」的扩张压力（R-030，High × Critical，
   分类 Product governance）。
4. 二进制 DOCX 直接比较没有意义（ZIP 顺序、时间戳、rId、文档属性
   可变），需要规范化策略支撑确定性验证（R-019）。

Phase 0 已建成 `qa/` 基础设施与两个门禁工具并完成首轮实证
（见 §3），`docs/update/QUALITY_STRATEGY.md`（六域质量策略全文）、
配套 `docs/update/PRODUCT_SCOPE.md` 与
`docs/update/COMPATIBILITY_MATRIX.md` 已就位。本 ADR 记录最终决策。

## 2. 决策

1. **采纳六域证据制**（QUALITY_STRATEGY 全文）：D1 Syntax & Parser、
   D2 Semantic & Validation、D3 Template & Layout、D4 Academic Objects
   & Fields、D5 Compatibility & Visual、D6 Release & Non-functional；
   每个正式用例保存可审计证据（build report、docx、XML 片段、PDF、
   截图、哈希与环境信息）。
2. **采纳 `qa/` 目录与用例 ID 规范**：`TF-D<domain>-<area>-<sequence>`，
   ID 永不复用、废弃保留记录；目录为 `qa/catalog/`（机器可读用例）、
   `qa/fixtures/`、`qa/baselines/`、`qa/tools/`、`qa/results/<run-id>/`
   （`qa/README.md`）。现状：8 个种子用例已入 `qa/catalog/cases/`
   （index.json：P0×4、P1×4；suite `pr-gate` 4 例、`nightly` 8 例）。
   golden/基线更新必须人工审查，不得在 CI 自动接受。
3. **`qa/tools/openxml_validate.py` 与 `qa/tools/no_repair_open.py`
   纳入 PR 门禁**：
   - 每个 E2E DOCX 必须过 openxml_validate 全部 13 项检查
     （ZIP 完整性、[Content_Types].xml、relationship 目标存在性、
     relationship ID 重复、XML well-formed、`w:document` 根元素、
     书签配对、field 配对、media 引用、sectPr 存在、样式引用、
     numbering 引用、footnote 引用）；退出码 0/1/2 语义固定。
   - D3/D4 域的关键对象（TOC/SEQ/REF/PAGE/Bookmark/OMML/三线表/
     节属性）必须具备结构化断言（XPath/关系/字段指令级），不接受
     「文件存在即通过」。
   - **Word no-repair 为 Alpha 起门禁**：Alpha 出口准则包含
     「Word 打开无修复提示」（QUALITY_STRATEGY §13），由
     no_repair_open 产出 JSON 证据；WPS 结果的
     `pending-human-review` 需人工确认闭环，不计自动失败。
4. **采纳 DOCX 规范化策略**（QUALITY_STRATEGY §7 十步：安全解包 →
   OPC 校验 → XML canonicalization → namespace prefix 规范化 → 时间戳
   剔除/替换 → rsid 规范化 → relationship 稳定排序映射 → media 内容
   哈希 → semantic manifest → 关键 XPath/parts/manifest 比较）；
   不得为快照稳定删除有业务意义的字段、样式或 section 信息。
   两次 clean build 的规范化结果一致是 GA 门槛（执行摘要「质量门槛」）。
5. **兼容矩阵定级**：Word = **primary**、WPS = **compatible**、
   LibreOffice = **preview**。等级验收标准与逐能力证据矩阵见
   `docs/update/COMPATIBILITY_MATRIX.md`；模板包
   `compatibility.target_apps` 与之对齐（primary 恰允许一个，
   TEMPLATE_PACKAGE_SCHEMA_V2 §3.2）。关键 finalization 不以
   LibreOffice 替代 Word（R-007/R-028 退路）。
6. **产品范围（R-030 范围纪律）**，全文见
   `docs/update/PRODUCT_SCOPE.md`：
   - V1 聚焦**中文学位论文（本科/硕士）**；
   - **CLI 优先**，桌面 UI 后置到 V1.1；
   - **AI 不进入编译链路**（AGENTS.md §1.3），AI Proposal/Diff/
     Approval 工作流为 V1.2（R-023）；
   - 模板策略：**单学校模板先闭环**（Alpha 一个真实学校模板完整
     编译、Word 无修复提示），Beta 扩到三个代表模板；
   - 期刊排版、LaTeX 输入、云协作、模板市场等为 out-of-scope；
   - 新需求必须说明替换哪个现有优先级（R-030 预防条款原文）。

## 3. 决策理由（实证依据）

**门禁工具已实证可用**（Phase 0 产物，`qa/README.md` 与
`spikes/phase0/fields/REPORT.md`）：

- openxml_validate 在 fields spike 两份生成态样本（
  `complete-thesis-example.docx`、`minimal-hut.docx`）与
  docx-template spike 三份产物（reference.docx、
  reference-inheritance.docx、shell.docx、merged.docx）上全部
  **13/13 通过**（fields 报告 §3；docx-template 报告 §0）。
- no_repair_open 首轮实测（`spikes/phase0/fields/results/no-repair.json`
  及各变体 JSON）：
  - **Word 16.107.2**：complete-thesis-example 复核 **pass**
    （11.14s，无对话框）；同时实证了首开弹窗行为——带
    `w:updateFields` 或 `w:fldChar w:dirty` 的生成态文档首开必弹
    「字段更新确认框」（模态，阻塞 150s 被工具判 fail），两者**各自
    独立触发**，全部剥掉后静默打开（3.41s/3.78s pass）。工具目前
    无法区分「字段更新确认框」与「修复提示」，已记录为工具改进点
    （fields 报告 §4、§10.5）。
  - **LibreOffice 26.2.3.2**：两份样本均 pass（headless 转 PDF，
    351,940 / 139,451 字节）。
  - **WPS**：无可靠脚本接口，工具只产出 `pending-human-review`，
    需人工确认（qa/README.md）。
- LO finalizer 路径的已知限制也已实证（fields 报告 §6）：LO 刷新会
  改写 TOC 指令（丢 `\z \u`、新增 `\f`）、剥掉 SEQ `\r` 钉值、移除
  `w:updateFields`、重写页眉页脚部件，且刷新后 openxml_validate
  **失败**（LO 引用的 TOC1-3/IndexLink/FootnoteCharacters 样式未在
  渲染器 styles.xml 定义）——这正是兼容矩阵必须分级、且 LO 只能
  作 preview 的直接证据。
- 现有测试基线：pytest 482 passed / 4 failed（4 个失败均为
  LibreOffice runner 环境缺陷：darwin 硬编码 `/tmp`，
  CURRENT_STATE_AUDIT §4/§5 D-09）；ruff 仅 `tmp/` 3 个 I001。
  说明核心链路质量足以承载门禁，缺的是门禁本身（D5 域）。

**为什么证据制而非测试清单**：QUALITY_STRATEGY §15 明确「只有用例
文本、没有 fixture 和证据的测试清单，不算真正建立质量体系」；
R-016 的退路是「暂停功能扩张，补齐 fixture 和门禁」。六域模型把
Word 对象真实性（D4）、办公软件兼容（D5）、离线/安全/可复现（D6）
提升为与功能测试同级的一等公民。

**为什么 Word=primary**：分页由字体、渲染引擎、Office 版本共同影响
（R-007），跨引擎像素一致不可承诺；学校端权威提交环境是 Word，
final-word profile 依赖本机 Word（R-027）。LibreOffice 视觉基线仅作
相对回归（R-028），WPS 以 compatible 定级并逐项列已知差异。

## 4. 备选方案与拒绝理由

1. **只跑单元测试 + 文件存在性冒烟**：拒绝——R-016（High ×
   Critical）；无法发现字段、关系与版式错误，无法回答执行摘要
   「质量门槛」八条中的任何一条。
2. **以 LibreOffice headless 作为唯一兼容基线**：拒绝——LO 与 Word
   行为差异已实证（§3：finalizer 改写字段、样式缺口导致校验失败）；
   R-028 明确「LibreOffice 仅作为 preview」。
3. **对三应用做同级承诺**：拒绝——WPS 无脚本接口、OOXML 支持差异
   未知项多（R-014），同级承诺会制造无法兑现的验收义务；
   分级承诺（primary/compatible/preview）才是可审计的。
4. **直接二进制 diff 做确定性验证**：拒绝——ZIP 时间戳、rId、
   docProps 等合法可变（QUALITY_STRATEGY §7 首段）；采用规范化 +
   semantic manifest 比较。
5. **V1 同步启动 UI 与 AI**：拒绝——R-022（UI 过早绑死 Core API）
   与 R-023（AI 破坏确定性/隐私）均为 High/Critical；执行摘要决策 1
   已将版本拆为 Engineering Preview/Alpha/Beta/GA + V1.1 UI +
   V1.2 AI。
6. **V1 覆盖博士/期刊/LaTeX 输入等更宽场景**：拒绝——R-030；
   保持核心扩展点但不提前实现（R-030 退路）。

## 5. 后果

### 正面

- 「什么算通过」首次有了机器可判的定义：PR 门禁（unit/contract/
  lint/small E2E/OOXML 结构/security fast suite）+ Alpha 起 Word
  no-repair 门禁 + 分级兼容矩阵。
- 用例、证据、基线有统一目录与 ID 规范，发布门禁（QUALITY_STRATEGY
  §13 四级 Release Gate）可审计、可归档、可哈希固化。
- 产品范围书面化，版本路线与出入准则明确（PRODUCT_SCOPE.md），
  R-030 有了可执行的拒绝依据。
- DOCX 规范化策略使「两次 clean build 一致」（R-019）成为可检验
  的 GA 门槛。

### 负面 / 代价

- 门禁维护成本：golden/基线人工审查、兼容矩阵逐版本重测、证据
  归档都是持续投入（R-017 基线过脆风险需同步治理：semantic XPath、
  区域 mask 与容差）。
- WPS 证据依赖人工确认（pending-human-review），RC 阶段需要排期
  人力。
- no_repair_open 无法区分弹窗类型，在 finalizer 策略定型前
  （ADR-0005），Word 首开弹窗会使门禁产生「语义为字段更新确认」的
  fail，需要工具改进或配合 final 产物门禁化。
- 范围纪律会拒绝合理但非 V1 的需求，需要治理流程承接（记录、
  排入 V1.1/V2 评估）。

### 后续行动

1. 将 openxml_validate + no_repair_open 接入 CI PR 流水线（fast
   suite）；Word no-repair 在 Alpha 起作为正式门禁项。
2. 改进 no_repair_open：区分「字段更新确认框」与「修复提示」
   （读取对话框文本，spike 已验证 System Events 可行）。
3. 渲染器无条件补齐 TOC1-3/IndexLink/FootnoteCharacters 等 LO 会
   引用的样式，使 final-auto 产物也能过 openxml_validate
   （fields 报告 §8 建议；与 ADR-0005 联动）。
4. 实现 `qa/tools/normalize_docx.py`（QUALITY_STRATEGY §7 十步）并
   接入 D6-REP 用例。
5. 逐阶段填充 `qa/catalog/cases/`（每个 P0/P1 需求至少关联一个
   用例）与 `qa/baselines/`；WPS 人工确认纳入 RC 检查单。
6. 按 PRODUCT_SCOPE.md 的版本出入准则执行 gate 评审；范围变更
   一律走「替换哪个优先级」的书面流程。
